Network Protocol Specification (UDP)

Version: 1.0
Status: Stable
Applies to: R-Type (client/server)
Transport: UDP (connectionless), Boost.Asio

1. Overview

The R-Type networking layer is a lightweight, UDP-based protocol designed for real‑time game traffic. It prioritizes low latency, predictable bandwidth, and graceful degradation under packet loss. Reliability and ordering are provided selectively via per‑packet flags to avoid the overhead of TCP for time‑sensitive updates.

This document specifies:

  • Packet wire format and endianness
  • Reliability semantics (unreliable, reliable unordered, reliable ordered)
  • Sequence, ACK, and ACK bits piggyback
  • Retransmission policy and timers
  • Ordered delivery buffering rules
  • Event model surfaced to the application
  • Error handling and interoperability constraints (Linux/Windows)

References in code:

  • protocol/ProtocolTypes.hpp
  • protocol/Protocol.hpp
  • protocol/Protocol.cpp

2. Design Goals

  1. Real-time first: time-sensitive updates (e.g., positions) must not block on retransmits.
  2. Selective reliability: caller chooses reliability per message.
  3. Piggyback ACKs: minimal overhead via (ack, ack_bits).
  4. Ordered channel: support a sequenced stream for critical gameplay messages.
  5. Simplicity: single socket, minimal state, portable (Linux/Windows).

3. Transport

  • Protocol: UDP (IPv4/IPv6) via Boost.Asio.
  • MTU budget: MAX_PACKET_SIZE_BYTES = 1200 bytes to avoid IP fragmentation on typical paths.
  • Sockets: Single asynchronous socket with async_receive_from and async_send_to.
  • Threading: I/O served by Boost.Asio’s io_context; optional dedicated IO thread (start_io()/stop_io()).

4. Packet Header (Wire Format)

All multi-byte integers are big-endian on the wire (network byte order).

+-------------------- Packet Header (packed) --------------------+
| uint16 message_type | uint8 flags | uint8 reserved(0x00) |
+------------------------+---------------+-----------------------+
| uint32 sequence | uint32 ack | uint32 ack_bits |
+---------------------------------------------------------------+
| uint16 payload_length |
+---------------------------------------------------------------+
| <payload bytes...> up to MAX_PACKET_SIZE_BYTES |
+---------------------------------------------------------------+

C++ struct (host order before serialization):

struct packet_header_t {
uint16_t message_type; // application-defined type id
flag_t flags; // reliability/order semantics
uint32_t sequence; // 0 for UNRELIABLE, else >0
uint32_t ack; // last sequence seen from peer
uint32_t ack_bits; // bitmask for ack-1 .. ack-32
uint16_t payload_length; // bytes following the header
};

4.1 Fields

  • message_type: 16-bit application identifier. Serialized with htons.
  • flags (enum class flag_t : uint8_t):
    • 0 = UNRELIABLE
    • 1 = RELIABLE_UNORDERED
    • 2 = RELIABLE_ORDERED
  • sequence:
    • 0 for UNRELIABLE packets.
    • Monotonic (per sender) for reliable packets; starts at 1.
  • ack / ack_bits (piggyback):
    • ack = highest contiguous sequence number received from peer.
    • ack_bits = 32-bit window where bit 0 acknowledges ack-1, bit 31 acknowledges ack-32.
  • payload_length: size of the payload; htons on send, ntohs on receive.

4.2 Serialization

  • Function: serialize_packet_ack(packet_t, peer_state*).
  • Converts sequence, ack, ack_bits to big-endian.
  • Copies header + payload into a single contiguous buffer for send.

5. Reliability & Ordering

Reliability is per-packet, chosen by the caller at send time.

5.1 Flags

  • UNRELIABLE
    • sequence = 0
    • No retransmission, not tracked in pending table.
  • RELIABLE_UNORDERED
    • Retransmitted until acknowledged or attempts exhausted.
    • Delivered to app as soon as received (no sequencing).
  • RELIABLE_ORDERED
    • Retransmitted and delivered in sequence based on sequence.
    • Out-of-order packets are buffered until missing packets arrive or timeout-based advancement is triggered.

6. Sequence, ACK, and ACK Bits

6.1 Sender sequences

  • Global per-sender 32-bit counter (_next_sequence), starts at 1.
  • Only applied to reliable packets. Unreliable packets keep sequence = 0.

6.2 Receiver ACK window

  • State per peer: peer_receive_state_t maintains:
    • last_received (highest seen)
    • ack_bits window
    • expected_sequence (for ordered delivery)
  • On packet seq:
    • If seq is newer than last_received:
      • Shift ack_bits left by diff = seq - last_received
      • Set bit for seq-1 if diff >= 1
      • Update last_received = seq
    • Else (older or duplicate):
      • Compute dist = last_received - seq
      • If 1 <= dist <= 32, set corresponding bit in ack_bits.

Implementation: update_peer_ack_window().

7. Retransmission Policy

  • Timerless design: retransmission is driven by the application calling process_pending(now).
  • Constants:
    • RESEND_MS_INTERVAL = 200 ms
    • MAX_RETRANSMIT_ATTEMPTS = 32

7.1 Pending table

  • Stored in _pending_sends: map<sequence, pending_send_t>.
  • On reliable send:
    • Insert entry with attempts = 1 and last_sent = now.
  • On ACK reception:
    • Remove the acknowledged ack and any additionally acknowledged by ack_bits.

7.2 Resend/Fail workflow

  • If now - last_sent >= RESEND_MS_INTERVAL: schedule resend and increment attempts.
  • If attempts >= MAX_RETRANSMIT_ATTEMPTS:
    • Remove from table and emit TRANSMIT_FAILED event with the original packet.

8. Ordered Delivery

For RELIABLE_ORDERED, the receiver enforces in-order delivery:

State: expected_sequence, buffered<seq, (packet, time)>, waiting_since.

Rules (see handle_ordered_delivery()):

  1. If seq == expected_sequence
    • Deliver immediately, increment expected_sequence, update waiting_since, then flush any newly contiguous buffered packets.
  2. If seq > expected_sequence
    • Buffer (seq, packet, now) until the gap is filled or timeout advances the window.
  3. If seq < expected_sequence
    • Duplicate or late arrival: ignored for delivery (already delivered or advanced).

8.1 Timeout-based advancement

  • After waiting 10 * RESEND_MS_INTERVAL (i.e., 2000 ms) without progress:
    • If buffer not empty:
      • Advance to the smallest buffered seq ≥ expected_sequence.
    • Else:
      • expected_sequence++ (skip one).
    • Flush contiguous buffer if possible.

8.2 Buffer expiry

  • Entries older than 100 * RESEND_MS_INTERVAL (i.e., 20,000 ms) are dropped.

9. Event Model

Core emits core_event_t with:

  • event_type_t::PACKET_RECEIVED
    • Payload: packet_t (header, payload, remote)
  • event_type_t::TRANSMIT_FAILED
    • Payload: transmit_failed_t (sequence, message_type, payload, remote)
  • event_type_t::CONNECTION_LOST
    • Payload: monostate (receive error); used to notify upper layer
  • event_type_t::CONNECTION_ESTABLISHED
    • Notified by upper layers (optional)

APIs:

  • bool is_event() — non-blocking check
  • bool wait_event(milliseconds timeout) — blocking wait
  • bool get_event(core_event_t &out) — pop next event

10. Application Message Types

packet_header_t::message_type is application-defined (16-bit).
The game layer maps higher-level events (e.g., create/move/destroy, input) to numeric IDs and packs payload bytes accordingly. See GameProtocolTypes.hpp.

Examples (game layer):

  • CREATE_ENTITY = 1
  • MOVE_ENTITY = 2
  • DESTROY_ENTITY = 3
  • PLAYER_INPUT = 100 (Exact list may vary per build; the core does not interpret these values.)

11. Example Wire Packet

Example: RELIABLE_ORDERED move update

Assumptions:

  • message_type = 0x0002 (MOVE_ENTITY)
  • flags = 0x02 (RELIABLE_ORDERED)
  • sequence = 0x00000005
  • ack = 0x00000009
  • ack_bits = 0b0000...0101 (acks 8 and 6 behind ack=9)
  • payload_length = 0x000C (12 bytes)
  • Payload (12 bytes): entity_id (u32), x (u32), y (u32)

Hex (header then payload):

00 02 02 00
00 00 00 05 00 00 00 09 00 00 00 05
00 0C
[ 00 00 00 2A 00 00 03 E8 00 00 07 D0 ]

Notes:

  • Header fields are big-endian.
  • Payload endianness is application-defined; in our implementation, payload integers are serialized as big-endian via helpers in utils.

12. Error Handling & Resilience

Receiver-side:

  • Short datagram (bytes_transferred < sizeof(header)): drop silently, reschedule receive.
  • I/O error in receive handler:
    • Emit CONNECTION_LOST, then reschedule receive if socket remains open.
  • Malformed payload: upper layers should validate per message type.
  • ACK processing: non-existent sequences in pending table are ignored.
  • Backpressure: application controls polling rate; no internal sleeps.

Sender-side:

  • Socket closed / not initialized: send_packet() returns std::errc::not_connected.
  • Resend exhaustion: emit TRANSMIT_FAILED and drop from pending table.

13. Timing & Tuning

  • RESEND_MS_INTERVAL (default 200 ms): global resend cadence.
  • MAX_RETRANSMIT_ATTEMPTS (default 32): per-sequence cap.
  • Ordered delivery:
    • Progress timeout: 10 * RESEND_MS_INTERVAL = 2000 ms
    • Buffer expiry: 100 * RESEND_MS_INTERVAL = 20000 ms

These values are balanced for WAN latency spikes and moderate loss. For LAN-only play, intervals can be reduced.

14. Security Considerations

  • UDP lacks connection semantics; always validate message type and payload sizes.
  • Avoid trusting client-reported positions or authority; server should be authoritative.
  • Rate-limit per remote if necessary (DoS mitigation).
  • Prefer dropping malformed/out-of-window data rather than attempting recovery.

15. Interoperability & Platform Constraints

  • Endianness: all header fields use network byte order (big-endian).
  • Linux: no special prerequisites.
  • Windows:
    • Winsock initialization is handled (WSAStartup/WSACleanup).
    • Error codes are mapped via Boost.System; behavior aligned with Linux paths.
  • Sockets: IPv4 and IPv6 supported; bind uses address family of local address.
  • Buffering: internal receive buffer is pre-sized to MAX_PACKET_SIZE_BYTES.

17. Versioning & Extensibility

  • The protocol is version-less at header level to minimize overhead.
  • Backward compatibility should be handled by message_type evolution and application-layer negotiation.
  • If a header version is introduced, reserve the reserved byte for a version tag.

20. Glossary

  • ACK: Acknowledgment of receipt.
  • ACK bits: 32-bit window summarizing recent acknowledgments.
  • Ordered delivery: Delivery to application strictly in sequence order.
  • Piggyback: Embedding ACK data in normal outgoing packets.
  • Pending table: Map of not-yet-ACKed reliable packets.
