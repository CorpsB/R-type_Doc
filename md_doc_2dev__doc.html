Developer Documentation

This document complements the Doxygen API reference and offers a high‑level overview of the Advanced Simple Game Engine (ASGE) and the R‑Type game. It is intended to help new contributors understand the architecture, major subsystems and workflows needed to build, extend and maintain the codebase. For wire‑level details of the networked gameplay see the Network Protocol, and for the rationale behind technology choices see the Technical & Comparative Study.

1 Architecture overview

ASGE is deliberately modular. At its heart is EngineCore, which orchestrates the lifecycle of the application by owning a Services object. Services exposes a dozen interfaces (timer, renderer, audio, network, world, script, etc.) and each has at least one concrete implementation. The game depends only on these interfaces—not on the implementations—so components can be replaced or mocked as needed. This follows the principle of dependency inversion.

1.1 Subsystems and layers

The engine is organised into layers that initialise in a strict order. Each layer depends only on those initialised before it. A typical breakdown is shown below.

Layer Interfaces / components Role and dependencies
Core runtime ITimer, IDebug, IJob Logging and metrics, the game clock (fixed and variable step), and a job system for multithreaded tasks. These are initialised first to support subsequent systems.
Input & Events IInput, IEvent Normalises keyboard/mouse/gamepad input and dispatches events to interested systems.
Storage IStorage Abstracts asset loading (file system, memory).
Media IRenderer, IAudio Rendering and audio. The client uses Raylib backends; the server or test mode can use Null backends.
Gameplay World (ECS), IScene, IScript The ECS manages entities, components and systems; scenes orchestrate high‑level states (menu, level); the script manager loads JSON templates for entities, behaviours and maps.
Network INetwork, NetworkManager, NetworkChannel Handles client–server communication via channels. Channel 0 is reliable (entity creation/destruction); channel 1 is best‑effort (state snapshots). See the Network Protocol for packet formats.

1.2 Initialisation and main loop

EngineCore initialises subsystems in a defined sequence. After setting up debugging, timing and storage services, it creates the job pool, event bus, input layer, renderer/audio backends, script system, ECS world and finally the network manager. During runtime the engine ticks through a fixed‑update loop followed by variable‑step updates. A typical loop is:

while (engine.running()) {
timer.update(); // update fixed time and delta
network.poll(); // receive and dispatch packets
world.update(fixedDt); // run ECS systems
scripts.update(); // execute script hooks
scene.update(); // update active scene logic
renderer.render(); // draw frame (client only)
audio.mix(); // mix audio (client only)
debug.flush(); // write logs
}

The server runs the same loop but uses NullRenderer and NullAudio backends. Callbacks (onInit, onUpdateFixed, etc.) may be registered via EngineHooks to inject game‑specific logic without modifying the core.

1.3 Entity–Component System (ECS) and scripting

Gameplay is built on an Entity‑Component‑System (ECS). Entities are lightweight identifiers; components are simple data structures (e.g., position, sprite, health); systems encapsulate logic and operate on entities whose component signatures match their requirements. This architecture allows data‑oriented storage and easy extension. The World API registers systems and processes them each tick.

Scripts extend the ECS with declarative behaviours. JSON templates in assets/scripts/game/entities/ define archetypes: sets of components plus optional behaviour hooks. Scripts also define maps (levels) and resource descriptors for sprites and audio. The ScriptManager parses these files, resolves inheritance (extends) and provides templates to the EntityFactory. Behaviour hooks such as on_create, on_update, on_position or on_death can emit actions (e.g., play a sound, spawn an entity or destroy itself).

1.4 Networking and game protocol

The engine supports multiple transports: UDP for online play, Loopback for local testing and Null transport for headless operation. NetworkManager registers one handler per channel and delivers raw packets to GameProtocol for decoding. Channel 0 is configured as reliable and guarantees ordered delivery (entity creation, destruction); channel 1 is best effort and carries high‑frequency state snapshots. Packets consist of a small header with an opcode, entity identifier and component type followed by a payload. Typical opcodes include EntityCreate, EntityDestroy, ComponentAdd, ComponentUpdate, ComponentRemove, StateSnapshot and Inputs. See the Network Protocol for a complete description of the packet layout and opcodes.

2 Compiling and running the project

ASGE relies on CMake, Conan and a C++20 compiler. The engine is packaged as a static library in lib/asge, and the game client and server live in rtype/. All third‑party dependencies are managed through Conan. For a quick start, use the helper scripts provided in lib/asge/tools (see the top‑level README for specific commands). Alternatively, you can build manually:

# create a build directory
mkdir -p build && cd build
# install dependencies and generate CMake files
conan install ../lib/asge --build=missing -s build_type=Release
cmake ../lib/asge -DCMAKE_BUILD_TYPE=Release
# build the engine library
cmake --build . --target asge
# build the game
cd .. && mkdir -p rtype/build && cd rtype/build
conan install .. --build=missing -s build_type=Release
cmake .. -DCMAKE_BUILD_TYPE=Release
cmake --build . --target rtype-server --target rtype-client

Refer to the top‑level README for Windows commands and environment setup. Once the binaries are built, run the server and client as described in the README.

3 Extending the game

3.1 Adding a new enemy archetype

New entities are defined via JSON templates in assets/scripts/game/entities/. An archetype contains a unique id, a set of component attributes, and optional behaviour hooks. You can inherit from an existing archetype using the extends property to avoid repetition. For example, enemy_custom.json extends enemy_base.json, overriding only a few fields.

To create your own enemy:

  1. Define a sprite in assets/scripts/ressources/sprites/. Each sprite file references a texture under assets/files/textures/ and defines its dimensions and optional scaling.
  2. Create the entity template in assets/scripts/game/entities/ with a unique id. Specify components such as name, sprite, hitbox, health, damage, speed and direction, and add optional behaviour hooks (on_create, on_update, on_position, on_collision, on_death).
  3. Register sounds in assets/scripts/ressources/songs/ if your new archetype uses audio. Each file defines an id, a file link under assets/files/songs/, a volume and whether it loops.
  4. Spawn the enemy by adding entries in your level (see below). The LevelSpawner reads the spawn list and creates entities at the appropriate distances during gameplay.

3.2 Creating a new level

Levels are described in JSON files located in assets/scripts/game/maps/. Each map file contains an id, a total length and a list of spawns. Each spawn has:

  • distance: how far into the level the spawn should occur;
  • archetype: the id of the entity template to spawn;
  • position: an { x, y } object specifying the spawn coordinates;
  • layer: a render layer index (optional).

To create a new level:

  1. Copy level_1.json to a new file (e.g., level_2.json) and change the id and length fields.
  2. Edit the spawns array: add entries for your new enemy archetypes at appropriate distances and positions.
  3. Load the new level by adjusting the game logic (e.g., selecting your new map id when constructing LevelSpawner).

3.3 Adding a network module or message type

ASGE’s network stack is designed for extensibility. If you need a new form of communication (for example, a high‑bandwidth update channel or a reliable chat channel) you can implement a new channel or transport:

  1. Implement a transport by deriving from INetwork or NetworkChannel to support a new socket type or reliability policy. Implement methods to open sockets, send/receive packets and handle disconnects.
  2. Register your channel during initialisation. In EngineCore::initNetwork(), call services._network->registerChannel(id, reliable) and services._network->setHandler(id, callback) to hook your channel into the GameProtocol.
  3. Define new opcodes in GameProtocol::MsgType. Add functions to encode/decode your message. Both client and server must handle the new messages and update the ECS accordingly.
  4. Synchronise state: send high‑frequency updates on an unreliable channel and critical events on a reliable channel. Maintain ordering within each channel.

When designing new protocols, preserve the binary message structure (opcode + entityId + componentType + payload) to ensure compatibility. See the Network Protocol for guidance on existing message formats.

4 Conventions and contribution guidelines

4.1 Coding style

  • Use C++20 features when appropriate (ranges, structured bindings, std::unique_ptr, std::optional). Avoid raw pointers except when interfacing with C libraries.
  • Interfaces are prefixed with a capital I (e.g., IRenderer, INetwork). Classes use PascalCase; variables and functions use snake_case; constants are UPPER_SNAKE_CASE.
  • Follow RAII for resource management; avoid manual new/delete. Use std::vector/std::array for containers and std::optional for optional return values.
  • Provide Doxygen comments for all public classes and functions. Document parameters, return values and ownership semantics. Complement the generated API with high‑level docs such as this one.
  • Keep each module independent. High‑level modules should depend on interfaces only; low‑level modules should not know about game logic. Use Services for dependency injection and avoid global singletons.
  • Test deterministic behaviour: network and ECS code must behave the same on different machines. Use headless mode for unit tests.

4.2 Git workflow

  • Use feature branches for each change (e.g., feature/add-enemy, bugfix/renderer-crash). Avoid committing directly to main.
  • Write descriptive commit messages (present tense, imperative mood) and group related changes together.
  • Before opening a pull request, run unit tests and code formatting tools (clang‑format, clang‑tidy). Ensure the project builds on both Linux and Windows.
  • Dependencies are managed by Conan; avoid committing generated build files or third‑party libraries into the repository.
  • Rebase onto the latest main branch before merging and request code reviews.

4.3 Branching and release strategy

Adopt a simple branch model:

  • **main** – stable branch containing the last release candidate.
  • **develop** – integration branch where features are merged after review.
  • **feature/*** – short‑lived branches for new features or bug fixes.
  • **release/*** – branches created from develop when preparing a release. Only accept bug fixes and documentation updates; merge into main when ready.

4.4 Formatting and tooling

  • Integrate clang‑format and clang‑tidy into your editor or CI pipeline. Use a team‑defined style (LLVM or Google style) if no .clang-format exists.
  • Enable all compiler warnings and treat them as errors (-Wall -Wextra -Werror). Fix warnings immediately rather than suppressing them.
  • Run static analysis tools (AddressSanitizer, UBSan) regularly to catch undefined behaviour.

4.5 Documentation practices

  • Keep this developer documentation up to date when adding new systems or changing the architecture.
  • Provide Markdown documentation for high‑level concepts and workflows in the doc/ folder. Doxygen should generate an API reference from source code, but contextual explanations (diagrams, tutorials, rationale) must be written manually.
  • Ensure that anyone can build and extend the project using only the README, this document, the network specification and the technical study.

By following the structure and guidelines described above, you can confidently contribute to the R‑Type project: extend the gameplay by adding new enemies or levels, develop new network features, and maintain the engine in a clean, modular and testable manner. The ASGE architecture is intentionally designed to separate concerns and facilitate learning.
