Technical & Comparative Study

This document explains and justifies the technological choices behind the ASGE engine and the networked R‑Type game. It compares alternatives and describes the main algorithms, data structures, storage strategies and security measures used in the project. For details of the network protocol, see the Network Protocol, and for an overview of the engine’s architecture and how to extend it, see the Developer Documentation.

1. Language choice: Why C++?

Performance and control – Real‑time games require predictable frame rates and low latency. C++ provides direct control over memory and system resources, enabling developers to avoid unnecessary allocations and tailor data structures for cache efficiency. Zero‑cost abstractions such as templates and constexpr allow the code to remain expressive without incurring runtime overhead. High‑level languages or managed runtimes (Java, C#, Python) impose garbage collection and additional layers that can introduce unpredictable pauses or lower throughput. C++ is also widely supported on desktops and consoles, making it easier to port the project to multiple platforms.

Alternatives considered

  • Java / C# – Automatic memory management simplifies development but introduces garbage‑collector pauses and slower native interop. They also require large runtime dependencies that are undesirable for a lightweight game.
  • Python – Excellent for scripting or tooling but too slow and dynamic for the core of a real‑time game.
  • Rust – A modern systems language with strong safety guarantees. It eliminates many classes of bugs at compile time, but the team lacked experience with it and its ecosystem is younger than C++.

2. Transport protocol: Why UDP instead of TCP?

The project specification mandates the use of UDP for gameplay communications. UDP is connectionless and has minimal overhead; there is no handshake or retransmission at the transport level. This results in lower latency and jitter, which are critical for a fast‑paced shooter where missed updates are acceptable because the next snapshot arrives quickly. By contrast, TCP guarantees in‑order delivery and retransmits lost packets, causing head‑of‑line blocking and noticeable lag when packets are dropped. The engine implements its own reliability layer on top of UDP (channel 0) to guarantee delivery of critical events, while channel 1 carries best‑effort snapshots. This hybrid approach delivers low latency without sacrificing correctness for important game events.

Alternatives considered

  • TCP – Provides built‑in reliability and congestion control but suffers from handshake overhead and head‑of‑line blocking. Packet loss can introduce large delays, making it unsuitable for continuous real‑time updates.
  • Quic / WebRTC – Modern protocols that build reliability and congestion control on top of UDP. They are designed for general Internet applications and introduce significant complexity. At the time of the project, no stable C++ library met the portability requirements.
  • Game‑oriented libraries (Enet, RakNet) – Provide reliability and ordering on top of UDP with features tailored to games. Some are proprietary or unmaintained, and they impose their own abstractions that may conflict with the ECS architecture. Implementing reliability directly with Boost.Asio offered greater control and learning value.

3. Network layer: Boost.Asio vs alternatives

The engine uses Boost.Asio for networking and asynchronous I/O. Boost.Asio is a de facto standard for modern C++ networking and hides platform differences between BSD sockets and Winsock, allowing the code to remain portable. It supports asynchronous operations, timers and multithreading, which are essential for a game server that must process network events without blocking the main loop. Boost.Asio exposes low‑level UDP access while allowing the engine to build its own reliability layer. The library is mature, widely adopted and influenced the forthcoming standard C++ networking library.

Alternatives considered

Alternative Drawbacks

4. Rendering and multimedia: Why raylib?

Raylib is a lightweight C library with a simple, readable API. Its design philosophy is “learn by doing”, making it ideal for educational and mid‑sized projects. Creating a window and drawing a sprite requires only a few lines of code, reducing boilerplate and letting developers focus on game logic rather than low‑level OpenGL calls. Raylib runs on Windows, Linux, macOS and even WebAssembly, satisfying the project’s cross‑platform requirement. It offers built‑in support for textures, audio, fonts and basic 3D without requiring separate modules. Although raylib is implemented in C, it integrates easily into C++ and fits naturally with the engine’s ECS and service‑based architecture. Raylib delivers sufficient performance for a 2D shooter while remaining lightweight; it can be statically linked to produce small executables.

Comparative study of rendering libraries

Library / Engine Pros Drawbacks
Raylib Lightweight, open source, simple API; cross‑platform; built‑in support for textures, audio and fonts; easy integration with C++ and ECS; excellent documentation. Limited advanced features; some customisation may require direct OpenGL calls.

After evaluating these options, raylib provided the best balance between simplicity, portability and sufficient features for a networked 2D shooter.

5. Game architecture: ECS and data structures

The engine uses an Entity–Component–System (ECS) pattern to decouple game objects from their behaviour. Entities are represented by lightweight identifiers. Components are plain data structures that store attributes such as position, velocity, sprite, health or damage. Systems operate on entities whose signatures match the components they require. This separation improves cache locality and allows for dynamic composition of behaviours. The engine initialises services (timer, input, renderer, world, network) in a defined order and runs a main loop where it updates systems, polls the network and flushes debug output. See the developer documentation for diagrams and examples.

Entity management

Entities are managed by an EntityManager that stores metadata in a vector along with a free‑list of reusable IDs. Each entity has a generation counter, a signature bitset and an active flag. Creating or destroying an entity is an O(1) operation. Signatures are updated when components are added or removed and are used to filter entities for systems.

Component storage

Components are stored in dense arrays inside a ComponentArray. For each component type, a vector holds component instances; two index maps translate between entity IDs and component indices. When a component is removed, the last element is swapped into the removed slot to keep the array dense, achieving O(1) insertion and removal. This design maximises cache locality during system iteration.

System management

Systems are registered with a SystemManager and stored in a map keyed by system type. Each system has an execution signature represented by a bitset of required components. When an entity’s signature changes, the manager updates the affected systems by adding or removing the entity from their internal lists. Systems can be enabled or disabled at runtime. Bitwise operations on signatures allow constant‑time checks to determine whether an entity should be processed by a system.

Algorithms and game logic

Several common algorithms underpin the gameplay:

  • Sorting and spawning – The LevelSpawner loads enemy spawn events from JSON and sorts them by distance using std::sort. During the level, it iterates through the sorted vector and spawns entities when the player reaches the appropriate distance. This ensures deterministic and efficient spawning.
  • Bitmask filtering – Systems check whether an entity should be processed by performing a bitwise AND between the entity’s signature and the system’s signature. This constant‑time operation yields high performance.
  • Asynchronous storage – StorageManager uses a worker thread and a queue to perform asynchronous file reads. A mutex and condition variable protect shared resources, ensuring thread safety and avoiding blocking the main loop.
  • Event‑driven network polling – The network layer uses an asynchronous poll function to process packets without blocking gameplay. Handlers are registered per channel; when a packet arrives, the appropriate handler decodes it into ECS operations. See the network specification for details.

6. Storage techniques

The engine abstracts storage via an IStorage interface and a StorageManager. This design allows different backends, such as local filesystem, cloud storage or in‑memory devices. The StorageManager performs synchronous reads/writes for simple operations and asynchronous reads using a worker thread and callback. File contents are loaded into std::vector<uint8_t>, ensuring proper ownership and RAII semantics. Resources such as textures, sounds and level definitions are stored in JSON or binary files within the assets directory. At startup, the storage manager loads configuration and script files; during gameplay, level spawns are read as needed. Loaded resources are cached until no longer required to avoid repeated file reads.

7. Security considerations

Memory safety and error handling

Although C++ offers great performance, it is prone to undefined behaviour if misused. The engine mitigates this by using smart pointers (std::unique_ptr, std::shared_ptr) for ownership semantics, following RAII patterns to ensure deterministic resource release and wrapping exceptions in custom error types that carry context. Components and systems check bounds and return optional values when entities are invalid. All dynamic allocations are guarded with try/catch to handle out‑of‑memory errors. This improves robustness and prevents crashes due to memory corruption.

Network integrity and buffer management

The binary protocol uses fixed‑size headers and explicit integer sizes to ensure that both ends agree on the layout. When decoding packets, the engine validates the opcode and component type and ensures that payload sizes match expected component structures. Unrecognised or malformed packets are logged and discarded rather than processed. The network layer catches recoverable errors and logs them; by separating channels into reliable/unreliable streams, the engine prevents untrusted clients from flooding the server with large snapshots, because the server can drop excessive unreliable packets without affecting critical state. See the network specification for details on error handling.

Handling untrusted clients

Clients should not trust one another. The server maintains authoritative control over entity creation, movement validation and game physics. Clients send input commands; the server validates them and broadcasts the resulting state. To prevent resource exhaustion or denial‑of‑service, the server limits the rate of packet processing per peer and disconnects clients that violate protocol expectations. Parsing of data files (e.g. JSON for level templates) uses robust libraries with proper error handling to prevent buffer overflows or injection attacks.

8. Summary

The R‑Type project uses C++20, Boost.Asio, raylib and an ECS architecture to build a modular, cross‑platform game engine. These technical decisions favour performance, simplicity and control. By selecting UDP with a custom reliability layer, the engine meets the stringent latency requirements of a real‑time shooter while maintaining robustness and extensibility. Data structures such as dense component arrays, bitsets and maps ensure fast operations, while asynchronous storage and network polling keep the main loop responsive. The project’s security strategy emphasises proper memory management, exception handling and network integrity. Together, these choices create a solid foundation for both the R‑Type game and future projects built on the engine.
