Network Protocol

This document specifies the binary UDP protocol used by the ASGE engine to synchronise game state between clients and servers. It defines the packet structure, message types, reliability channels and guidelines for implementing a compatible client. For an overview of the engine architecture, see the Developer Documentation. For the reasoning behind these design choices, see the Technical & Comparative Study.

Overview

ASGE’s network layer abstracts transport‑level details behind an INetwork interface. A NetworkManager owns a transport socket and dispatches packets to registered handlers for each logical channel. Two channels are registered by default:

Channel Reliability Typical use case
0 Reliable Entity creation, destruction, component updates
1 Unreliable Periodic state snapshots

The protocol uses UDP because low latency is critical for real‑time games. Reliability is implemented by the engine on channel 0 rather than by the transport itself; see the technical study for details.

Packet structure

Every datagram sent over UDP begins with a network header (NetHeader) used by the reliability layer:

Field Type Description
seq u32 Sequence number of the outgoing reliable packet (channel 0).
ack u32 Last sequence acknowledged back to the sender.
flags u8 Bit‑field: FLAG_RELIABLE marks a packet requiring acknowledgement; FLAG_ACK_ONLY marks an acknowledgement packet containing no payload.
channel u8 Logical channel identifier (0 for reliable, >0 for best effort).
reserved u16 Reserved for future use and alignment.

Immediately following the NetHeader is a Game Protocol Header that describes the gameplay payload:

Field Type Description
version u8 Protocol version (currently 1).
msg_type u8 Message type / opcode (see below).
flags u8 Reserved for future flags (compression, encryption, etc.).
channel u8 Repeats the logical channel for redundancy.
seq u32 Message sequence number for ordering game messages.

The payload follows the game header. Variable‑length integers (varUInt) are used to reduce bandwidth for small values. All fields are little‑endian. Clients and servers must validate header fields and ignore unrecognised opcodes or malformed data; invalid packets must never crash either program.

Message types and opcodes

The engine currently defines the following message types. Unless noted otherwise, messages on channel 0 are reliable and those on channel 1 are best effort.

Message type (msg_type) Channel Purpose and payload structure
EntityCreate (0x01) 0 Spawn a new entity on the client. Payload: entity_id (u32) and pattern_id (string) specifying which archetype to instantiate.
EntityDestroy (0x02) 0 Remove an entity from the client. Payload: entity_id (u32).
ComponentAdd / ComponentUpdate 0 Add or update one or more components on an entity. Payload: entity_id (u32), component_count (varUInt) and a list of component blobs. Each blob begins with a component_type_id (varUInt) followed by the serialized component data. ComponentAdd creates missing components; ComponentUpdate modifies existing ones.
ComponentRemove 0 Remove a component from an entity. Payload: entity_id (u32) and component_type_id (varUInt).
StateSnapshot (0x03) 1 Periodic snapshot of the world state. Payload: tick (u32), entity_count (varUInt) and, for each entity, an entity_id, a component signature bitset and zero or more component blobs. Snapshots may be dropped or arrive out of order; each represents a complete state replacement.
Inputs (reserved) 0 Client‑to‑server input replication. Not currently used; reserved for future extensions.

EntityCreate messages cause the client to create a local entity using the specified archetype. EntityDestroy instructs the client to remove an entity. ComponentAdd/Update synchronise one or more components; the difference lies in whether new components are created or existing ones updated. ComponentRemove deletes a component. StateSnapshot messages on channel 1 transmit a complete snapshot of the game world, including entity signatures and component data. Snapshots are sent at a regular cadence (e.g., 20 Hz) and may be dropped without acknowledgement.

Channels and reliability

Channel 0 (Reliable) uses a stop‑and‑wait protocol: each reliable packet includes a sequence number and must be acknowledged. The FLAG_RELIABLE bit in the NetHeader marks such packets. The ack field in the next outgoing packet acknowledges receipt of the last reliable message from the peer. Only one reliable packet can be in flight per peer; additional sends are queued by the network manager. Retransmissions occur after an adaptive timeout.

Channel 1 (Best effort) sends packets without acknowledgement. Messages on this channel (such as state snapshots) may be lost, duplicated or arrive out of order. The game logic should treat each snapshot as a complete state replacement and can drop older snapshots when a newer one arrives.

Additional channels can be registered with different reliability policies. When designing new messages, preserve the binary message structure (headers followed by payload) to ensure compatibility. See the developer documentation for details on registering channels.

Connection and disconnection

To start a server, the application calls a method to open a UDP socket and listen on a port. A client connects by sending a first reliable packet to the server’s address and port. The server assigns a unique connection ID for each client and replies with an acknowledgement, establishing the session. Both peers maintain independent send (seq) and receive (ack) counters per channel.

Either side may close the connection by calling a shutdown function, which stops polling the socket and clears connection state. On packet loss, the network manager retransmits reliable packets until acknowledged. Inactive peers are dropped after a timeout. Loopback and Null transports are available for local testing and headless operation.

Error handling and invalid packets

UDP datagrams may be lost, duplicated or reordered. The reliable layer mitigates this for critical messages, but clients and servers must still validate incoming data. Unknown opcodes or mismatched payload sizes should cause the packet to be ignored, not processed. Header fields must be checked to ensure they fall within expected ranges. Robust error handling is essential to avoid crashes and security issues when communicating with untrusted clients. The project specification explicitly requires that malformed messages never compromise the stability of the server or client.

Implementing a new client

To write a client that can interoperate with the R‑Type server, follow these guidelines:

  1. Transport setup – Open a UDP socket and send an initial reliable packet (e.g., an empty packet on channel 0) to the server. Await the server’s acknowledgement to establish sequence numbers.
  2. Packet parsing – For each received datagram, read the 12‑byte NetHeader. Verify the channel, flags and sequence numbers. If FLAG_ACK_ONLY is set, update the acknowledgement state and skip the payload.
  3. Game message decoding – Remove the network header and read the GameProtocol header. Dispatch based on msg_type and decode the corresponding payload. Use variable‑length decoding for integers and strings.
  4. State application – On EntityCreate and EntityDestroy, spawn or remove entities. On ComponentAdd, ComponentUpdate or ComponentRemove, update the local ECS accordingly. On StateSnapshot, update each entity’s state and discard older snapshots if a newer one arrives.
  5. Sending inputs – (Optional) encode local input states into an Inputs message and send it on a reliable channel. The server can then validate and broadcast the resulting state.
  6. Reliability – Maintain per‑peer sequence numbers for reliable messages. For each reliable message sent, wait for an acknowledgement and retransmit after a timeout.
  7. Graceful shutdown – When quitting, send a final reliable packet to notify the server, then close the socket. Dispose of any resources associated with the network manager.

By following this specification, a third party can implement a compatible client or server without inspecting the original code. For further information on how the network layer integrates with the ECS and game logic, see the developer documentation.
