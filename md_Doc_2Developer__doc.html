R-Type — Developer Documentation

‍This document describes the internal architecture and developer-facing guidelines for the r-type project. It is tailored to this repository (client/server split, ECS stack in Common/ECS, UDP protocol in Common/Protocol, and Raylib client UI) and complements the auto-generated API docs (Doxygen).

  • Language: C++17
  • Build: CMake (+ Conan)
  • Networking: Boost.Asio (UDP)
  • Graphics: raylib
  • Platforms: Linux and Windows
  • Repos paths referenced below: Client/, Server/, Common/, Configs/, Tests/, Doc/

1. High-Level Overview

R-Type is implemented as a client–server application:

  • The Server (Server/) owns the authoritative simulation, runs game logic, and broadcasts state over UDP.
  • The Client (Client/) renders the game using raylib, handles input/UI, and syncs to the server state.
  • The Common (Common/) module hosts shared code: ECS core (Common/ECS), the network Protocol (Common/Protocol), and utilities.

Key goals

  • Deterministic & responsive simulation under UDP constraints.
  • Modular ECS for extensibility and maintainability.
  • Cross-platform support (Linux/Windows).
  • Separation of concerns: rendering in client; simulation and authority on server; shared code in Common/.

3. ECS Architecture (Common/ECS)

The ECS is split into managers and systems:

3.1 Core Managers

  • EntityManager
    • Files: Common/ECS/EntityManager.*
    • Responsibilities: allocate/recycle entity IDs; keep signatures (bitset of components per entity); track active state.
    • API highlights:
      • createEntity(), destroyEntity(id)
      • getSignature(id), setSignature(id, bitset)
  • ComponentManager
    • Files: Common/ECS/ComponentManager.*
    • Responsibilities: register component types and store their dense arrays via ComponentArray<T>.
    • O(1) operations by indirection tables: owner→index and index→owner.
    • Template API: registerComponent<T>(), addComponent<T>(id, value), getComponent<T>(id)
  • SystemManager
    • Files: Common/ECS/SystemManager.*
    • Responsibilities: register systems, assign execution signatures (required components); maintain system _filtered_entities.
    • On signature change, it inserts/removes entities into system sets.
  • Coordinator
    • Files: Common/ECS/Coordinator.*
    • Façade binding managers; updates signatures and notifies systems when components are added/removed.

3.2 Components (Attributes)

Located in Common/ECS/Components/Attributes/:

  • Position.hpp (x, y)
  • Direction.hpp (dx, dy, normalized)
  • Speed.hpp (speed scalar)
  • Sprite.hpp (sprite id/metadata for client)
  • Health.hpp, Damage.hpp, Score.hpp, Frequency.hpp, etc.

‍Components are POD-like structs to keep storage dense and cache-friendly.

3.3 Systems

  • MovementSystem
    • Files: Common/ECS/Systems/MovementSystem.*
    • Signature: Position + Direction + Speed
    • Logic: pos += dir * speed * ticks with rounding; ignore entities missing any component.
  • CollisionSystem + CollisionWorld
    • Files: Common/ECS/Systems/CollisionSystem.*, Worlds/CollisionWorld.*
    • Spatial hashing into cells (via makeKey/decodeKey) with configurable PIXELS_PER_CLUSTER.
    • Build grid with entity hitboxes; test intra- and inter-cell pairs using SAT-like axis separation on oriented boxes.

3.4 Extending the ECS

Add a new component

  1. Create Common/ECS/Components/Attributes/MyComponent.hpp.
  2. Register in your game bootstrap: coordinator.registerComponent<MyComponent>();
  3. Add to entities: coordinator.addComponent<MyComponent>(id, {{...}});

Add a new system

  1. Derive from System into Common/ECS/Systems/MySystem.{{hpp,cpp}}.
  2. Register: auto sys = systemManager.registerSystem<MySystem>();
  3. Define signature bits: systemManager.setSignature<MySystem>(sig);
  4. In the game loop: call sys->update(coordinator, dt/ ticks...).

4. Networking Architecture (Common/Protocol)

4.1 Low-level UDP Core: <tt>Protocol</tt>

  • Files: Common/Protocol/Protocol.{{hpp,cpp}}, ProtocolTypes.hpp, Utils/utils.*
  • Single UDP socket managed by a singleton Protocol.
  • Main responsibilities:
    • init(local_address, port): create socket, bind, schedule async receive.
    • send_packet(remote, message_type, flag_t reliability, payload): serialize header + payload and post async_send_to.
    • Reliability for non-unreliable flags: sequence numbers, ACK + ACK bits piggybacking, retry with capped attempts (MAX_RETRANSMIT_ATTEMPTS, RESEND_MS_INTERVAL).
    • Event queue: PACKET_RECEIVED, TRANSMIT_FAILED, CONNECTION_* exposed through is_event / wait_event / get_event.

Pending reliable sends

  • Tracked in _pending_sends with attempt counters and last_sent.
  • process_pending(now) scans and resends when due or emits failure events.

Ordered delivery

  • Per-peer state peer_receive_state_t holds expected_sequence, buffered, ack_bits.
  • handle_ordered_delivery flushes contiguous sequences, buffers gaps, expires stale entries.

4.2 Game-level Facade: <tt>GameProtocol</tt>

  • Files: Common/Protocol/GameProtocol.{{hpp,cpp}}, GameProtocolTypes.hpp
  • Adds typed payloads and message ids: CREATE_ENTITY, MOVE_ENTITY, DESTROY_ENTITY, PLAYER_INPUT, etc.
  • Serializers: serialize_* and try_deserialize_* functions to pack/unpack payloads.
  • Translates core events to game_event_t categories.

5. Client Architecture (Client/)

  • Raylib-based rendering and input:
    • Game/Scenes implements a minimal scene manager with MainMenu and OptionsMenu.
    • Game/Inputs/InputManager centralizes input mapping.
    • Game/Resources/ResourceManager loads assets (textures, fonts).
    • Game/Settings/GameSettings stores configurable client parameters.

Typical frame

  1. Poll Protocol events, update local ECS state.
  2. Step gameplay systems (MovementSystem, collisions if client-side prediction is enabled).
  3. Render via raylib.

6. Server Architecture (Server/)

  • Entry point: Server/main.cpp
    • Parses CLI flags (-h, -d, -dd, -ddd, -port=, -ip=, -path=).
    • Loads Configs/DefaultServ.cfg when no args, and flags override file values.
    • Starts rtype::server (see Rtype.hpp/.cpp) and calls run().

Server responsibilities

  • Maintain authoritative ECS world.
  • Integrate Protocol to receive player inputs and broadcast snapshots.
  • Apply rate controls: tick frequency, resend windows, snapshot throttling.

7. Performance Notes

7.1 ECS Storage & Cache Locality

  • ComponentArray<T> uses dense vectors with swap-remove to keep arrays contiguous.
  • Two indirection vectors:
    • _component_to_owner (index → entity)
    • _owner_to_component (entity → index or INVALID)
  • Benefits:
    • O(1) add/remove/lookup in the hot path.
    • Friendly to cache prefetchers during system iteration.

7.2 Collision World

  • Spatial hashing into cells sized by PIXELS_PER_CLUSTER reduces pair checks.
  • Axis separation tests operate on 4 corners with pre-normalized axes.
  • Only checks neighbor cells with larger keys to avoid duplicate pairs.

7.3 Networking

  • UDP with optional reliability means:
    • Lower latency than TCP.
    • Application-level control over retransmission and ordering.
  • Piggybacked ACKs minimizes overhead for reliability on game traffic.
  • No internal timers for periodic resend: process_pending(now) lets the host control pacing and avoid contention with the render thread.

7.4 Multithreading & IO

  • Protocol::start_io() runs io_context in a dedicated thread guarded by an executor work guard.
  • Avoids blocking the main thread; keep critical sections in _pending_mutex / _peer_mutex short.
  • Use lock-elision patterns (copy-before-unlock) on resend to reduce contention.

7.5 Allocation & Copies

  • Prefer emplace into ECS arrays.
  • Reuse std::vector<uint8_t> buffers for send/recv paths when possible.
  • Keep payloads small: aim under ~1200B (MAX_PACKET_SIZE_BYTES) to fit within typical MTUs.

8. Windows & Linux Constraints

  • Sockets
    • Windows requires WSAStartup/WSACleanup; handled inside Protocol::init()/shutdown().
    • Address parsing uses boost::asio::ip::make_address with error_code on both platforms.
  • Threads
    • std::thread and Boost.Asio are portable; ensure stop_io() joins and avoids self-join.
  • Build
    • CMake presets differ: check conan-default vs conan-release usage.
    • Compilers:
      • Linux: GCC/Clang with -std=c++17.
      • Windows: MSVC 2022 recommended.
  • Filesystem
    • Config default path: Configs/DefaultServ.cfg (ensure permissions and path separators for Windows).

9. Adding Features

9.1 New Message Type (network)

  1. Add ID in GameProtocolTypes.hpp::game_message_type_t.
  2. Define payload struct.
  3. Implement serialize_*/try_deserialize_*.
  4. Extend GameProtocol::retrieve_package switch to map to a game_event_type_t.
  5. Handle in server/client application layer.

9.2 New System (gameplay)

  1. Create Common/ECS/Systems/MySystem.{{hpp,cpp}} derived from System.
  2. Register in bootstrap; set execution signature.
  3. Call update each tick in server loop (authoritative) and optionally in client for prediction.

9.3 New Component

  • As described earlier; ensure you set/unset signature bits via Coordinator.

10. Testing

  • Unit tests live in Tests/ and use Criterion.
  • Suggested: add tests for:
    • ComponentArray<T> insertion/removal/has/get.
    • Protocol ACK window logic (update_peer_ack_window, ordering buffer).
    • Collision SAT edge cases and grid mapping makeKey/decodeKey.

11. Logging & Error Handling

  • Common/Utils/Error.* wraps exceptions with contextual where strings.
  • Server main catches rtype::exception::Error and prints [ERROR] - <where>: <msg>.
  • Prefer returning std::error_code from operations that may fail without being exceptional (e.g., init, send_packet).

12. Configuration & CLI

  • Default server config: Configs/DefaultServ.cfg.
  • CLI flags override config file values.
  • Example:
    ./r-type_server -d -port=8080 -ip=192.168.1.10 -path=server.cfg
