Contributing Guide

This document defines the contribution standards for this project.
It is written in RFC style to ensure consistency, quality, and clarity in collaboration.

1. Git Workflow

  • The project uses GitHub Flow:
    • main branch is protected and always deployable.
    • Development is done in feature branches:
      • feature/<name> for new features.
      • fix/<name> for bug fixes.
      • chore/<name> for maintenance or scripts.
    • Every change must go through a Pull Request (PR).
  • Merging rules:
    • At least one peer review is required.
    • CI checks must pass before merging.
    • Merge using Squash and Merge to keep history clean.

2. Commit Convention

All commits must follow the Gitmoji-based convention defined below.
No other emoji is allowed.

Format

  • Use the imperative form (e.g., *"Add feature"* not *"Added feature"*).
  • Provide details in the commit body if necessary.

3. Pull Requests

  • PR title must follow the same convention as commits (emoji + summary).
  • Each PR must include:
    • Description of changes.
    • Checklist of tasks completed.
    • References to related issues (e.g., Closes #42).

4. Code Style and Quality

  • Follow the project’s linter/formatter rules (see README.md).
  • Naming conventions:
    • Variables & functions: camelCase
    • Classes & components: PascalCase
    • Constants: UPPER_SNAKE_CASE
  • Every :bug: or :sparkles: commit must be covered by tests (:white_check_mark:).
  • Do not commit commented-out code (:fire: should be used instead).

5. Documentation

  • Documentation updates must be committed with :memo:.
  • API changes require corresponding updates in the docs.
  • Architectural changes must be explained with :building_construction: commits and, if needed, an Architecture Decision Record (ADR).

6. CI/CD and Releases

  • CI pipeline runs tests and linting on every PR.
  • The project follows Semantic Versioning (SemVer).
  • Releases are tagged from the main branch.
  • Release notes are generated from commit history (based on emojis).

7. Communication

  • Always open an Issue before working on a large feature.
  • Use Pull Requests for discussion and review.
  • Keep commit history clean and descriptive.

8. License

  • License-related changes must always be committed with :page_facing_up:.

Final Notes

This contribution guide is mandatory.
Commits or Pull Requests not respecting these rules will not be merged.
The objective is to maintain a clear, structured, and professional Git history while keeping collaboration efficient.
